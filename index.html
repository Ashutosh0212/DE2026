01What is a DBMS?

A Database Management System (DBMS) is a software suite designed to efficiently manage and access a structured collection of interrelated data, known as a database. This data typically represents information relevant to a particular enterprise or domain.

The primary objective of a DBMS is to make storage, retrieval and management of this information convenient and efficient.

02File-processing systems & their drawbacks

Database systems emerged to overcome the limits of early computerized data management. In the 1960s, universities stored information about instructors, students, departments and courses in plain operating-system files, and application programs were written to manipulate those files.

As needs evolved (e.g. introducing a new major like computer science), new programs and files were added. Over time the system grew more complex, with many files and custom programs for reading and writing records. Before DBMSs, this was the standard approach.

1. Data redundancy & inconsistency
Programs and files developed independently use different formats. The same data gets duplicated — a double-major student's contact details stored in both departments. This raises storage cost and causes inconsistency when updates are not applied everywhere.
2. Difficulty in accessing data
A clerk wants students in a specific postal code — no program exists. Either filter a full list by hand or ask for a new program. A follow-up request (only students with 60+ credits) needs yet another program. No flexible, ad hoc retrieval.
3. Integrity problems
Consistency constraints (e.g. a department's account balance must never go below zero) are buried in application code. Adding a new constraint means changing many programs — especially hard when constraints span multiple files.
4. Atomicity problems
Transferring 500 from department A to B may debit A, then crash before crediting B. Both must happen together or not at all. All-or-nothing behaviour is hard to guarantee with plain files.
5. Concurrent-access anomalies
Two clerks debit (500 and 100) a balance of 10,000 at nearly the same time. Both read 10,000 and write back 9500 or 9900 — instead of the correct 9400. Similarly, two students registering when the count is 39 both write 40, breaking the limit and losing one registration.
6. Security problems
Not every user should see all data — payroll staff shouldn't see academic records. With ad hoc programs piling up, enforcing access control is difficult.

These challenges led to the development of database systems.

03Database system

A database system consists of interrelated data plus software that lets users access and modify that data, while hiding the complexity of how it is stored. A key goal is to present an abstract view of the data, shielding users from low-level details.

04Data abstraction — three levels

LevelWhat it describesWho works here
View (highest)Only a portion of the database, tailored to a user or application. Hides logical structure and enforces security.End users, via application screens / queries
LogicalWhat data is stored and the relationships among it, independent of physical storage.Database administrators, developers
Physical (lowest)How data is actually stored, using complex low-level data structures (bytes, disk blocks).Handled by the database system

Analogy with programming-language types

type instructor = record
    ID        : char(5);
    name      : char(20);
    dept_name : char(20);
    salary    : numeric(8,2);
end;

Other record types in the same university example:

  • department — (dept_name, building, budget)
  • course — (course_id, title, dept_name, credits)
  • student — (ID, name, dept_name, tot_cred)
  • Physical: these records become blocks of storage — programmers usually don't see this.
  • Logical: the structure of each record type and their relationships are defined, like type definitions in code.
  • View: registrar clerks may see student information, but not instructor salaries.

05Schema & instances

As data is inserted or deleted, the database changes. The data stored at a specific moment is an instance. The overall structure is the schema, which changes rarely.

Analogy: schema ≈ variable declarations (with types); instance ≈ the values of those variables at a point during execution.
  • Physical schema — how data is actually stored.
  • Logical schema — what data is stored and relationships among it. Most important for applications, since programs depend on it.
  • View schemas (subschemas) — how different users see subsets of the data.

The physical schema can usually change without affecting programs. When application programs don't depend on the physical schema and need not be rewritten if it changes, the system exhibits physical data independence.

06Data models

A data model is a conceptual framework describing a database's structure — data, relationships, constraints and semantics — across the physical, logical and view levels.

Relational model
Data in tables (relations) of rows and columns. Record-based: each table stores fixed-format records. The most widely used model today.
Entity–Relationship (ER) model
Describes the database with entities and relationships among them. Commonly used for conceptual design.
Object-oriented model
Extends the ER model with OOP ideas: encapsulation, methods, object identity.
Object–relational model
Combines object-oriented features with the relational model; supported by several modern systems.
Semistructured model
Data items of the same type may have different attributes. XML is widely used to represent such data.

Older hierarchical and network models preceded the relational model but were tightly tied to implementation details. They are rarely used today and are not covered in this course.

07Database languages

A database system provides a DDL to define the schema and a DML to query and update data. In practice both are part of one language, such as SQL.

Data-Manipulation Language (DML)

Used to retrieve, insert, delete or modify data.

  • Procedural DML — user specifies what data is needed and how to get it.
  • Declarative DML — user specifies only what is needed; the system figures out how. Easier to use, but the DBMS must optimize data access.

A query is a DML statement that retrieves data; the query part of a DML is often just called a query language.

Data-Definition Language (DDL)

Defines the schema, storage structures, access methods and constraints. Common integrity constraints:

  • Domain constraints — restrict allowed values for an attribute.
  • Referential integrity — values in one relation must correspond to values in another.
  • Assertions — general conditions that must always hold.
  • Authorization — which access (read, insert, update, delete) each user has.

This metadata lives in the data dictionary, which the system consults before any data access or modification.

Think about it: the DDL interpreter parses and records schema definitions in the data dictionary, while the DML compiler translates queries into a low-level execution plan for the query engine. Why is one interpreted and the other compiled?

08Data storage & querying

A database system has two main components:

  • Storage manager — interface between low-level data and applications. Manages GBs–TBs of data on disk (main memory can't hold it all), organizes it to reduce costly disk I/O, and translates DML into file-system commands.
  • Query processor — translates high-level, nonprocedural queries and updates into efficient low-level operations, so users think in logical views, not physical storage.
Storage manager componentsRole
Authorization & integrity managerChecks access rights; enforces integrity constraints
Transaction managerKeeps the database consistent during failures; ensures conflict-free concurrent transactions
File managerAllocates disk space; organizes on-disk data structures
Buffer managerMoves data between disk and memory; decides what to cache. Critical when the database is much larger than memory

Data structures maintained by the storage manager:

  • Data files — the database itself.
  • Data dictionary — metadata, especially the schema.
  • Indices — map values to record locations for fast access (e.g. find an instructor by ID or name). Hashing is an alternative — faster in some cases, but not all.
Query processor componentsRole
DDL interpreterInterprets DDL statements; records definitions in the data dictionary
DML compilerTurns DML into an evaluation plan of low-level instructions. Since many equivalent plans exist, it performs query optimization to pick the most efficient
Query evaluation engineExecutes the low-level instructions to produce results

09Transactions

Several operations often form one logical unit of work. Transferring funds from account A to B needs both a debit and a credit — together or not at all.

A transaction is a sequence of operations that performs a single logical function and must satisfy:

AAtomicity
all or nothing
CConsistency
e.g. total balance unchanged
IIsolation
concurrent runs don't interfere
DDurability
effects survive failures

If the database is consistent before a transaction starts, it must be consistent after it finishes. Temporary inconsistency during execution is fine, but must be resolved by the end.

Defining transactions correctly is the programmer's job. A debit alone or a credit alone is not a transaction — neither moves the database from one consistent state to another.
  • Recovery manager — guarantees atomicity and durability; restores the database if a transaction fails.
  • Concurrency-control manager — preserves consistency when transactions run simultaneously.

Together these two form the transaction manager.

10Database architecture

Architecture depends on the underlying computer system: centralized, client–server (one server, many clients), parallel (multiprocessors) or distributed (geographically separated machines).

Most users access the database remotely over a network. Client machines are where users interact; server machines run the database system.

  • Two-tier: the application runs on the client and talks directly to the database server using query languages, often through APIs like ODBC or JDBC.
  • Three-tier: the client is only a front end, talking to an application server (usually via a forms interface). The application server holds the business logic and connects to the database. Better suited to large-scale and web applications.
